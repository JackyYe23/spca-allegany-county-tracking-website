# SPCA cat care checklist

The frontend uses vanilla HTML, CSS, and JavaScript. A small Python server stores submitted work in a local SQLite file; no Node setup, build, or package installation is required.

## Run locally

From this directory:

```powershell
python server.py
```

Open <http://localhost:8767/>. Enter a name, choose locations, check tasks, and click Submit my work. Refresh or reopen the page to review saved progress. Keep the same host and port to recover the same unfinished browser drafts. To choose a different port or record file, use `python server.py --port 8768 --database path/to/records.sqlite3`.

Versions share the same dated drafts and submitted history, so switching does not discard work or create submissions. - V3 is organized around a volunteer making a feeding round. It opens directly to all rooms and condos, with one feeding/drinking checkbox per location and Check all / Uncheck all beside the round title. Each location can open an inline exception and notes editor; only one editor opens at a time. Cat photos, search, per-cat issues, concern categories, and management flags use the same underlying records. A concern can be recorded without claiming the whole location's feeding check is complete. Optional condo enrichment is explicit and is never selected by Check all. Location order stays fixed while checking work. Only submitted checks receive the gray history state, and checked draft work is marked Not submitted. Validation opens the relevant location and focuses the incomplete exception field; failed saves retain the round.
- V3 keeps Task summary, Feeding round, Rooms, and Condos as direct navigation buttons, with Task summary first. Name, care date, and start time retain their original top placement; end time stays at the bottom left. Round and location headings use lighter weights. The round page has no progress block, and Task summary retains its original four cards with no extra feeding-round coverage block. Cleaning and other care remain available through Rooms and Condos.
- Large buttons replace tabs and the mobile section dropdown. In V1 and V2 no work section opens on load. Choose Task summary, Rooms, or Condos to reveal its content; clicking the active navigation button collapses it. Rooms and Condos show their location choices first. Each location's header only expands or minimizes the panel, with a short opacity fade that respects reduced motion. Room/condo changes do not use the moving page transition; Task summary retains its layout transition. Cleaning and Feeding toggles appear inside the expanded panel. Either work type can be toggled independently, with cleaning always before feeding. Each button includes an empty or checked square on its left, with its label centered in the button. Both labels use the same font, size, and weight. Narrow phones stack these work buttons so the indicators do not crowd the labels. Minimizing preserves work choices and answers. Work choices are independent for each location and restore with its draft.
- Name, care date, and start time appear once above the navigation and stay visible in every section.
- Task summary has its own date control for reviewing daily work without changing the current care date or draft. Each card shows its percentage above the left end of its progress bar. Only one Tasks panel opens at a time, with a teal outline on its card. On desktop, opening Tasks arranges the cards in a list on the left with the selected summary on the right; closing Tasks restores the grid. A brief view transition smooths opening, switching, and closing; browsers without that API use a fade, and reduced-motion preferences skip animation. Mobile keeps Tasks inside the selected card.

Room and condo choices stay visible above the selected location panels, with no Choose rooms or Choose condos button. Selection does not expand a panel or switch the one you have open; use a location's heading to expand it. Only one location opens per group. - Room feeding and condo feeding/enrichment use the same submitted-only gray state, completed-last ordering, and latest person/time details. Feeding and enrichment retain independent histories. Legacy partial feeding checks show Last checked without claiming that the whole location is complete. Overview location labels share their prefix, such as Room 2, 3, 8 or Condo 1, 2.
- Condo care keeps separate Feeding & drinking and Enrichment headings, including when completed items move below unfinished ones.

- Cleaning lists use two independent vertical columns from 900px upward and one column on smaller screens. Tasks read A–Z down the left column, then down the right, without shared row heights. Each task's label, instructions, and completion details stay together. One continuous list flows through the columns: unfinished tasks first, then submitted tasks, alphabetically sorted within each group, without visible category headings or a separate completed-items row. - Same-day drafts recover after refresh. Submission clears only the submitted work. Tasks, feeding checks, and enrichment remain editable, so checking them again creates a new contribution with a new ID and timestamp. Previous records remain in history; daily progress counts each task/check once. An empty draft does not resubmit earlier work. A new day starts with that day's draft, without carrying yesterday's name, selections, times, notes, or checkmarks into today. ## Storage and sample data

Open `feeding-preview.html` for the twelve-cat Room 6 example. It uses the same UI and styles with isolated in-memory data and does not access the main page's saved records.

Cat choices show a shared 42px portrait with rounded-square corners beside each name. Narrow phones use one column to keep names readable. The placeholder is stored at `assets/cat-placeholder.png` and was created with the built-in imagegen tool. Generation prompt: one square natural photograph of a friendly brown tabby, facing the camera, head and shoulders centered with full ears visible, soft daylight and a plain warm neutral background, recognizable at 42px, without text, logos, borders, or watermark.

`server.py` saves submissions in `.local-data/care-records.sqlite3`. The folder is excluded from Git and the database is not available as a downloadable website file. Records survive restarting the server and clearing browser site data. Existing browser records are imported once by their stable IDs; retrying a save does not duplicate it, while a new round of the same work creates a separate record. A failed database save keeps the work in its draft.

Unfinished drafts continue to autosave in browser localStorage (`spca.care.drafts.v1`), and submitted records have a browser cache (`spca.care.records.v1`). Serving the frontend with a plain static server still supports browser-only saving. The feeding preview remains isolated in memory and never contacts the database. Nothing is sent to SPCA or management.

Feeding entries retain `checkedAt`, the time the checkbox was marked, separately from the round's `submittedAt`. These times survive draft refresh and database storage. Check all preserves an already checked location's original entry time. Submission clears the submitted draft checks; repeating the work creates a new contribution ID and fresh check times without overwriting the earlier round. Old feeding drafts without a check time remain compatible and use the submission time as their fallback. All date/time validation and same-day draft rules still apply.

Cat names and the two condos are example data. Replace `rooms`, `condos`, and `cats` in `care-model.js` with the confirmed inventory, keeping stable IDs. Cleaning instructions preserve the original work in sixteen room steps and fourteen condo steps. Drafts and submissions now carry `taskCatalogVersion: 2`; older combined-task records are interpreted as their corresponding split steps without rewriting the original database records. New submissions record only the individual steps selected. Feeding and enrichment are unchanged. Dates and times use America/New_York.

This is a local UI development store. Authentication, live rosters, cross-device synchronization, management review, reporting, and the later Node backend remain future work. The JSON format stores contributions as individual task/check/exception/note entries with stable IDs and a feeding roster snapshot.
